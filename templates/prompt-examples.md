# プロンプト例（半日 S0-S7）

`[]` の中を自分の課題に置き換えて使います。最初に対象ファイル、目的、変更してよい範囲、期待する出力を伝えると、Copilot の回答を確認しやすくなります。

## 使い方

- まず短く聞き、足りない条件を追加して改善する。
- 変更を依頼する前に、対象ファイルと対象外を明確にする。
- 回答、差分、テスト結果、ドキュメントの内容は人が確認する。
- 機密情報、認証情報、個人情報はプロンプトに貼り付けない。

## S1: 最初の一歩（inline suggestions / Chat entry points）

### Inline suggestion を試す

エディターで対象ファイルを開き、コメントや関数名から候補を出させます。

```text
[対象ファイル] に、[やりたい処理] を表す短いコメントを書きます。
表示された inline suggestion を読み、意図に合う場合だけ採用してください。
採用後は、変わった行を自分で説明してください。
```

例:

```text
// 入力文字列の前後の空白を削除し、空なら既定値を返す
```

### Inline Chat で小さく直す

```text
選択した [対象箇所] を読みやすくしてください。
外部動作は変えず、変更理由を1文で説明してください。
```

### Quick Chat で用語を確認する

```text
[分からない用語またはエラー文] を、このリポジトリの文脈で初心者向けに説明してください。
まだファイルは変更しないでください。
```

### Chat View で流れを確認する

```text
[対象ファイル] の役割を3点で説明してください。
根拠となる関数名、ファイル名、確認すべき行を示してください。
まだファイルは変更しないでください。
```

## S2: プロンプト設計（Role + Task + Context + Format）

### 基本形

```text
Role: あなたは既存コードを安全に扱うペアプログラマーです。
Task: [対象ファイル] の [知りたいこと] を説明してください。
Context: このワークショップでは、既存コード理解、仕様整理、リファクタリングを練習しています。まだ変更はしません。
Format: 箇条書き3点と、確認すべきファイル名で答えてください。
```

### 悪い例を改善する

```text
次のプロンプトを、対象、目的、出力形式、変更可否が分かる形に改善してください。

元のプロンプト:
「このコードをいい感じにして」
```

### 条件を追加して聞き直す

```text
回答が広すぎました。
[対象ファイル] の [関数名または見出し] だけに絞り、実装から確認できる事実だけを説明してください。
推測は「推測」と明記してください。
```

## S3: 既存コードを理解する（`/explain` / `@workspace`）

### `/explain` で選択範囲を読む

```text
/explain
選択した処理を、入力、処理、出力の順に説明してください。
例外や境界値があれば、確認すべき観点も示してください。
```

### `@workspace` で影響範囲を探す

```text
@workspace [対象機能または関数名] はどのファイルから使われていますか。
主な呼び出し元、関連する仕様やテスト、確認すべきリスクを表で示してください。
まだファイルは変更しないでください。
```

### 仕様と実装を照合する

```text
[仕様書] と [実装ファイル] を比較し、現在の実装から確認できる動作を整理してください。
一致している点、不一致の可能性がある点、追加確認が必要な点に分けてください。
実装は変更しないでください。
```

## S4: 仕様整理とドキュメント生成（`/doc` / README draft）

### `/doc` で関数や処理を説明する

```text
/doc
選択した [関数または処理] に、利用者が誤解しない短い説明を追加してください。
引数、戻り値、副作用が分かるようにし、既存のコメントの書き方に合わせてください。
```

### 仕様メモを作る

```text
[対象ファイル] の現在の実装をもとに、[対象機能] の仕様メモを作ってください。
「できること」「入力」「出力」「例外・注意点」「確認方法」の見出しで、日本語で短くまとめてください。
推測した内容は含めず、コードから確認できる内容だけにしてください。
```

### README の下書きを作る

```text
[対象機能] を初めて使う人向けに README セクションの下書きを作ってください。
含める内容は、目的、使い方、実行例、注意点、確認方法です。
既存 README の文体に合わせ、まだファイルは変更しないでください。
```

## S5: テストを伴う安全なリファクタリング（`/tests` / refactor / `/fix`）

### `/tests` で保護する

```text
/tests
[対象ファイル] の [関数または機能] について、現在の動作を保護するテスト案を作ってください。
正常系、境界値、エラー系を分け、既存テストの書き方に合わせてください。
```

### 変更前に計画する

```text
[対象ファイル] の [改善したい点] を、外部動作を変えずにリファクタリングする計画を作ってください。
変更してよいファイルは [対象ファイル] だけです。
手順、確認するテスト、対象外を示し、まだ変更しないでください。
```

### 小さくリファクタリングする

```text
合意した計画に従って、[対象ファイル] の [対象箇所] だけをリファクタリングしてください。
依存関係の追加、無関係な整形、仕様変更はしないでください。
完了後に差分の要点と確認結果を示してください。
```

### `/fix` で失敗を直す

```text
/fix
次のテスト失敗を直してください。
原因を1文で説明し、修正は [対象ファイル] と関連テストだけに限定してください。

[エラーメッセージまたは失敗したテスト名]
```

## S6: 検証・責任ある AI・プライバシー

### 生成結果を検証する

```text
現在の差分をレビューしてください。
Issue の目的、対象ファイル、受け入れ条件、テスト、ドキュメントの正確性を確認し、問題を表で示してください。
確認できない点は「未確認」と書いてください。
```

### プライバシーと機密情報を確認する

```text
このプロンプトまたは差分に、機密情報、認証情報、個人情報、顧客固有情報が含まれる可能性がないか確認してください。
見つかった場合は、該当箇所、理由、削除または一般化する案を示してください。
```

### Responsible AI の観点で見直す

```text
この Copilot の提案を採用する前に、人が確認すべき点を整理してください。
正確性、セキュリティ、プライバシー、著作権、利用者への影響、テスト不足の観点で、短いチェックリストにしてください。
```

## 追加指示の例

```text
変更範囲を [対象ファイル] だけに絞ってください。関係のない変更は行わないでください。
```

```text
説明を日本語の初心者向けに直し、手順を3つ以内にしてください。
```

```text
提案した変更はまだ実行せず、変更予定のファイル、理由、確認方法だけを示してください。
```

```text
根拠となるコードやドキュメントが確認できない内容は削除し、確認事項として分けてください。
```
